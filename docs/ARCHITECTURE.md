# Web and remote architecture

`DocmonRuntime` is the composition root shared by the local TUI and the server. It owns one Docker client and registry factory, and exposes the existing service interfaces. `DocmonOperations` provides application operations for REST and MCP. Neither the runtime nor the local TUI requires HTTP authentication.

`Docmon.Server` hosts Watson 7 routes, bearer authentication, OpenAPI/Swagger, monitoring, durable request history and the terminal WebSocket. The route catalog supplies stable REST operation IDs and MCP names. The route registrar binds typed requests and attaches typed response schemas. Resource operations retain Docker identifiers; Docmon does not invent a second resource database.

The authentication model is intentionally one machine, one configured bearer credential, one full-control principal. This implements the requested environment-token model rather than the generic multi-tenant/user/RBAC system in the broader requirements. Request identity is stored as a typed `RequestContext`. Authentication compares SHA-256 hashes with a constant-time comparison. Bearer material is excluded from API responses and redacted from journal headers and captured bodies.

Voltaic's streamable HTTP server runs in the same process on a private loopback listener. Watson exposes `/mcp` on the public API port and forwards session/protocol/replay headers and streaming responses. Both listeners verify bearer authentication. The private port is never published by Compose, and a startup port conflict fails the host before its public listener starts. The MCP handler calls the same application service as REST, with the same camelCase JSON result content. CLI/exec failures set MCP `isError` and retain the command exit code.

Interactive sessions create a Docker exec with stdin and TTY enabled, then use an explicit HTTP-upgraded duplex connection. This avoids a legacy Docker.DotNet chunked-stream path that can read output without delivering working stdin on newer engines. Watson WebSockets bridge that stream to xterm.js and the remote TUI. The first WebSocket frame carries the bearer token; it is never placed in a URL. Invalid first-frame credentials are rejected before creating Docker execs. Terminal resize negotiation remains future work.

`RemoteDocmonClient` implements the TUI's existing service interfaces over REST. The local TUI is pinned to its local socket or named pipe and ignores `DOCKER_HOST`; `--server` opts into an authenticated remote connection. Remote file copies use tar transport between the TUI client and the Docker container, so client paths remain client paths. The JSON copy operations exposed to agents use server host paths. Remote pull/exec output is returned at completion; metrics/events poll every two seconds.

Request journals are daily JSONL files, not domain database entities. They persist across restarts, retain 30 days, restrict local file permissions on Unix, redact credentials and sensitive JSON fields, and cap bodies at 4096 characters. The API serves the most recent 1000 summaries and a separate full-record inspector to avoid transferring captured bodies on every dashboard poll. Docker events retain 1000 items and metric history retains 10000 samples in memory.

The React dashboard uses one authenticated fetch client, protected routes, shared tables and dialogs, i18next locale persistence, and shared theme state. Tables filter and paginate the current bounded resource arrays in the browser because the Docker-backed API returns snapshots. Core operations have purpose-built forms; API Explorer uses the live OpenAPI document, including binary archive uploads/downloads. The initial German, Japanese and Arabic catalogs translate core navigation/actions and fall back to English for remaining strings; the runtime also supports expanded pseudo-localization and RTL.

Compose pulls separately named server and dashboard images pinned to `v0.1.0`. Root build helpers publish both architectures and refresh the local image copies. Nginx proxies REST, terminal WebSockets and MCP streaming through one browser origin. The Docker socket grants the backend access to the host daemon; original Compose projects must be mounted at identical absolute paths for CLI operations. Persistent request journals use a named volume. The deployment consists of the backend and dashboard.

Reference implementations inspected: LiteGraph's dashboard shell and OpenAPI explorer for navigation and request/response inspection; LiteGraph's footer for the Discord invite; Voltaic's MCP HTTP server for transport/session behavior; Watson's OpenAPI and WebSocket sources.
